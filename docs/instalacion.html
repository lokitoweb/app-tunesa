Guía de instalación del ERP

Cómo instalar el sistema desde cero en un servidor nuevo: qué tecnología usa, qué hay que instalar, qué comandos correr y qué queda configurado solo. El resultado es un sistema vacío (sin datos de prueba ni marca de nadie), listo para que cada empresa lo configure a su modo.

3. Qué hace el instalador y qué hace el servidor

Una página web no puede tocar el sistema operativo (crear tareas programadas ni dar permisos): es así en cualquier sistema web, por seguridad. Por eso la instalación tiene dos partes:

Lo hace el instalador web (/install)Lo hace un comando en el servidor (server-setup.sh)
  • Revisa PHP, extensiones y permisos de carpetas
  • Crea el .env de producción completo y la clave de cifrado
  • Configura dominio, cookie segura y remitente del correo
  • Crea todas las tablas, los roles y los permisos
  • Crea el administrador principal
  • Se apaga solo al terminar
  • Revisa los programas del servidor
  • Corrige el dueño de storage/
  • Instala las tareas programadas (faltas, recordatorios, avisos push, comunicados)
  • Instala el despliegue automático
  • Permite recargar PHP después de cada actualización

4. Instalación paso a paso

En los comandos, reemplaza midominio.com por tu dominio y CLAVE por una contraseña larga y única. erp es el usuario de Linux dueño del sistema (puede ser otro nombre). Todo se corre como root salvo donde dice sudo -u erp.

1

Instalar los programas

apt update && apt -y install nginx mysql-server git unzip acl certbot python3-certbot-nginx \
  php8.2-fpm php8.2-cli php8.2-mysql php8.2-mbstring php8.2-xml php8.2-curl php8.2-gd \
  php8.2-zip php8.2-bcmath php8.2-intl php8.2-opcache
curl -sS https://getcomposer.org/installer | php && mv composer.phar /usr/local/bin/composer
curl -fsSL https://deb.nodesource.com/setup_22.x | bash - && apt -y install nodejs
Si php8.2 no aparece en tu versión de Ubuntu: add-apt-repository -y ppa:ondrej/php && apt update y repite. Sirve cualquier PHP 8.2 o superior (cambia el número en todos los comandos).
2

Crear la base de datos vacía

mysql -e "CREATE DATABASE erp CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci; CREATE USER 'erp'@'localhost' IDENTIFIED BY 'CLAVE'; GRANT ALL ON erp.* TO 'erp'@'localhost';"
printf '[mysqld]\nlog_bin_trust_function_creators = 1\n' > /etc/mysql/mysql.conf.d/erp.cnf && systemctl restart mysql
La segunda línea es obligatoria. Una tabla tiene un trigger que impide modificar las marcaciones ya registradas (auditoría) y MySQL 8 lo rechaza sin ese ajuste (error 1419). En MariaDB el archivo va en /etc/mysql/mariadb.conf.d/.
3

Descargar el código y compilar

adduser --disabled-password --gecos "" erp && mkdir -p /var/www/midominio.com && chown erp: /var/www/midominio.com
sudo -u erp -H bash -c 'git clone git@github.com:lokitoweb/app-tunesa.git /var/www/midominio.com/app && cd /var/www/midominio.com/app && composer install --no-dev --optimize-autoloader && npm ci && npm run build'
El repositorio es privado: antes, crea una deploy key para el usuario erp (sudo -u erp ssh-keygen -t ed25519) y agrégala en GitHub › Settings › Deploy keys, solo lectura.
4

Nginx y HTTPS

Crea /etc/nginx/sites-available/erp con este contenido (cambia el dominio y el socket de PHP si usas otra versión):

server {
    listen 80;
    server_name midominio.com www.midominio.com;
    root /var/www/midominio.com/app/public;
    index index.php;
    client_max_body_size 25M;

    location / { try_files $uri $uri/ /index.php?$query_string; }
    location ~ \.php$ {
        fastcgi_pass unix:/run/php/php8.2-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
        include fastcgi_params;
        fastcgi_read_timeout 120;
    }
    location ~ /\.(?!well-known).* { deny all; }
}
ln -s /etc/nginx/sites-available/erp /etc/nginx/sites-enabled/erp && nginx -t && systemctl reload nginx
certbot --nginx -d midominio.com -d www.midominio.com --redirect
5

Instalador web

Abre https://midominio.com/install con el dominio real y https (no con la IP): de esa dirección salen el dominio, la cookie segura y el remitente del correo. Son 5 pantallas:

  1. Requisitos: PHP, extensiones y carpetas con permiso de escritura (si algo sale en rojo, dice qué falta).
  2. Base de datos: los datos del paso 2 (botón para probar la conexión antes de guardar).
  3. Estructura: crea las tablas, los roles y los permisos (tarda 1 a 3 minutos).
  4. Plataforma y administrador: nombre del sistema, dominio de los correos de acceso, zona horaria y el administrador principal.
  5. Listo: el asistente se apaga y muestra el último comando del paso 6.
6

Configuración del servidor (una sola vez)

cd /var/www/midominio.com/app && sudo bash scripts/server-setup.sh --dry-run

Muestra lo que haría sin cambiar nada. Si se ve bien, aplícalo:

cd /var/www/midominio.com/app && sudo bash scripts/server-setup.sh

Tiene que terminar con Servidor listo. Se puede volver a correr cuando quieras: no duplica nada y no toca tareas de otros sistemas del mismo servidor.

7

Comprobar

sudo -u erp -H bash -c 'cd /var/www/midominio.com/app && php artisan app:check-production'

Revisa modo depuración, HTTPS, cookie segura, base de datos, cola, correo y que las tareas programadas estén corriendo. Al inicio el único aviso esperado es el del correo (sección 7). Espera 2 minutos después del paso 6 para que las tareas programadas den su primera señal.

5. El archivo .env

El .env guarda la configuración de cada instalación (dominio, base de datos, claves). No se copia de otro servidor ni se edita a mano: el instalador lo crea desde la plantilla de producción (.env.production.example) y completa solo lo que cambia en cada servidor.

ValorQuién lo poneDe dónde sale
APP_KEY (clave de cifrado)InstaladorSe genera al abrir /install por primera vez
APP_URL, APP_DOMAIN, SANCTUM_STATEFUL_DOMAINSInstaladorLa dirección con la que se abrió /install
SESSION_SECURE_COOKIEInstaladorActiva si se entró con https
DB_HOST, DB_DATABASE, DB_USERNAME, DB_PASSWORDInstaladorPantalla 2
APP_NAME, APP_TIMEZONEInstaladorPantalla 4
MAIL_FROM_ADDRESSInstaladorno-reply@ + el dominio
INSTALLER_ENABLED=falseInstaladorAl terminar: apaga el asistente
Producción: APP_ENV=production, APP_DEBUG=false, logs diarios, sesiones, caché y cola en MySQL, bloqueo de intentos de login, archivos privadosPlantillaYa vienen en .env.production.example
Correo SMTP (MAIL_MAILER, MAIL_HOST…)A manoDatos del proveedor de correo de cada empresa (sección 7)
Opcionales: MIGO_API_TOKEN, NUBEFACT_*, FINANCE_IGV_RATE, bancos y AFPOpcionalSin valor, la función queda apagada o con su valor por defecto. Migo y Nubefact también se configuran en el panel
¿Queda igual que el de un servidor en producción? Queda con la misma configuración de funcionamiento. Cambian solo los valores propios de cada servidor: dominio, base de datos, clave de cifrado, nombre y correo. Se revisaron una por una todas las variables que lee el sistema: las que no están en la plantilla tienen un valor por defecto que funciona.
Guarda una copia del APP_KEY en un lugar seguro. Con ella se cifran las claves guardadas en el panel (correo, Migo, Nubefact, Firebase). Si se pierde o se cambia, hay que volver a cargarlas.

6. Qué se crea en la base de datos

  • Todas las tablas: 91 migraciones, en orden, desde una base vacía. Son las mismas que usa producción.
  • 8 roles y 65 permisos del sistema (los mismos de producción).
  • Un solo usuario: el administrador que se crea en la pantalla 4.
  • Ningún dato de prueba: ni empresas, ni colaboradores, ni requerimientos. Cada empresa carga lo suyo.
Instalar desde cero no copia los datos de otro servidor. Para mudar una instalación que ya está en uso (con sus datos) hay que llevar la base (mysqldump), la carpeta storage/app y el APP_KEY; eso es una mudanza, no una instalación nueva.

7. Después de instalar (desde el panel)

  • Configuración › Marca y app: nombre, logos (claro y oscuro), colores, ícono del navegador, dominio de los correos de acceso. Hasta subirlos se ve un logo genérico.
  • Empresas: crear la primera empresa y su administrador.
  • Integraciones: correo SMTP para avisos y documentos a proveedores, consulta de RUC y DNI (token de Migo), facturación electrónica, webhooks.

La recuperación de contraseña usa el correo del .env. Edita estas líneas en /var/www/midominio.com/app/.env:

MAIL_MAILER=smtp
MAIL_HOST=smtp.tu-proveedor.com
MAIL_PORT=587
MAIL_USERNAME=usuario@midominio.com
MAIL_PASSWORD=la-clave-del-correo
MAIL_ENCRYPTION=tls
sudo -u erp -H bash -c 'cd /var/www/midominio.com/app && php artisan config:cache'

8. Actualizaciones automáticas

Después del paso 6 no hay que correr comandos para actualizar. Cada cambio sigue este camino:

1. PushSe sube un cambio a master en GitHub.
2. PruebasGitHub corre ~700 pruebas con SQLite y con MySQL 8, y compila el panel.
3. AprobadoSolo si todo pasa, GitHub mueve la rama production a ese cambio.
4. DespliegueEl servidor lo detecta en máximo 2 minutos y se actualiza solo.

En cada despliegue el servidor:

  • Respalda la base si hay migraciones.
  • Pone el sitio en mantenimiento unos segundos y corre las migraciones.
  • Actualiza roles y permisos, compila el panel si cambió y recarga PHP.
Si una prueba falla, producción no cambia: sigue en la última versión que pasó. Si el propio despliegue falla, vuelve solo al código anterior y deja el error en storage/logs/deploy.log.

Publicar al instante, sin esperar al cron, o reintentar un despliegue:

sudo -u erp -H bash -c 'cd /var/www/midominio.com/app && bash scripts/deploy.sh 2>&1 | tee -a storage/logs/deploy.log'

9. App móvil

La app no se instala en el servidor: se compila (APK para Android, IPA para iOS) y se reparte a los colaboradores. En GitHub se compila sola cada vez que cambia la carpeta mobile/.

  • Servidor al que se conecta: API_BASE_URL en mobile/env/<entorno>.json. Las apps ya instaladas también pueden cambiar de servidor desde el login (“¿Otra empresa o servidor?”).
  • Marca: nombre bajo el ícono, ícono, pantalla de arranque y logo salen de un kit de mobile/branding/<cliente>/. El kit default es neutro. Lo de adentro de la app (logo, colores, nombre) lo manda el servidor desde Marca y app.
  • Cliente nuevo: copiar mobile/branding/default, reemplazar las imágenes (mismas medidas), poner el nombre en brand.json y "BRAND" en su env/<cliente>.json.
  • Avisos push: necesitan un proyecto de Firebase; sin él la app funciona igual, sin notificaciones.

10. Si algo falla

SíntomaCausa y solución
El paso 1 del instalador sale en rojoFalta una extensión de PHP o permisos de escritura. El instalador dice cuál; instálala (apt install php8.2-<nombre>) y recarga.
La estructura falla con el error 1419Falta log_bin_trust_function_creators (paso 2). Agrégalo, reinicia MySQL y vuelve a “Crear estructura”.
No se puede iniciar sesión después de instalarSe instaló por http o por IP. Abre el sitio con el dominio y https; en .env revisa APP_URL y SESSION_SECURE_COOKIE.
check-production dice que las tareas programadas no correnFalta el paso 6, o hay que esperar 2 minutos.
Los cambios no llegan solosRevisa que las pruebas de GitHub estén en verde y mira storage/logs/deploy.log.
Git dice dubious ownershipSe corrió git como root. Úsalo siempre como el dueño: sudo -u erp -H …
No llegan correosMAIL_MAILER=log: completa los datos SMTP (sección 7).

11. Qué está probado y qué no

ParteEstado
Instalación desde cero con el instalador (base MySQL vacía, dominio nuevo, inicio de sesión, panel vacío y neutro, asistente apagado)Probado
Las 91 migraciones en MySQL 8 vacíoProbado en cada cambio
~700 pruebas automáticas del sistema, con SQLite y con MySQLEn cada cambio
server-setup.sh y el despliegue solo de lo aprobadoProbado en Linux y en el servidor actual
Pasos 1 y 4 (instalar paquetes de Ubuntu, Nginx y certificado)Comandos estándar; revisar en el primer servidor nuevo
Envío real de correos y consultas reales a MigoDependen de las credenciales de cada empresa
Las pruebas automáticas cubren las reglas del negocio y las pantallas, pero ningún sistema puede garantizar cero errores. Lo que sí está garantizado: nada llega a producción sin pasar esas pruebas en MySQL, y si un despliegue falla, el servidor vuelve solo a la versión anterior.
